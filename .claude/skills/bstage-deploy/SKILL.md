# 역할

이 레포의 코드를 포털을 통해 플랫폼에 올리고, 문제가 생기면 되돌린다. 이 스킬은 순서·판정·실패 갈래만 담는다. 플래그와 환경변수의 정확한 이름은 항상 `bstage <명령> --help`로 확인한다(기억으로 만들지 않는다).

# 전제 (여기서 어긋나면 나머지는 의미가 없다)

- **포털은 원격 저장소 기본 브랜치의 push된 커밋을 빌드한다.** 로컬 `dist/`를 업로드하는 것이 아니다. 로컬에만 있는 변경은 절대 반영되지 않는다.
- `bstage build`는 **로컬 확인용**이다. 배포 산출물은 포털이 다시 만든다.
- **레포 연결은 포털 화면에서만** 할 수 있다. 페이지 배치는 `bstage placement create`로 만든다(deploy 등급 토큰). 위젯(슬롯) 배치와 배치 삭제는 포털 화면 전용이다.
- 포털은 **레포를 연결해도 스스로 빌드하지 않는다.** 첫 빌드는 `bstage placement create`가(성공한 빌드가 없으면) 또는 `bstage deploy`가 건다.
- 배포는 여러 사람이 같은 스테이지를 건드린다. 적용 직전 상태를 확인하고, 중간에 바뀌었으면 멈춘다.

# 절차

## 1. 상태부터 본다 (읽기 전용)

```bash
bstage whoami
bstage list
```

- `whoami` — 어느 조직·스테이지에 어떤 역할로 로그인돼 있는지. 인증이 없으면 `bstage login`.
- `list` — 이 레포의 배치(라이브 버전·게시 상태)와 최근 빌드.
- 두 명령 모두 구조화 출력을 지원한다(`--json`, 명령별 `--help` 확인) — 값을 프로그램으로 읽어야 할 때 쓴다.

## 2. 갈래

### 2a. `bstage list`에 배치가 0건일 때

배포할 자리가 없다는 뜻이다(`bstage deploy`는 이 상태에서 빌드도 하지 않고 종료 코드 2로 멈춘다). 페이지 배치를 CLI로 만든다.

```bash
bstage placement create --template <산출물 이름> --path /<경로>
```

- `--template`은 빌드 산출물 이름이다 — sdk는 `src/pages/{이름}`, liquid는 `public/{user|admin}/{이름}`의 `{이름}`. 모르면 사용자에게 확인한다.
- `--path`를 생략하면 `/{이름}`이 된다. 경로는 사용자에게 확인한다(라이브 URL이 된다).
- 조직·스테이지·레포·surface는 `bstage link`로 만든 연결 정보를 그대로 쓴다.
- 성공한 빌드에 그 산출물이 없으면(첫 빌드 전, 새 페이지를 막 push) **push된 기본 브랜치 HEAD로 빌드부터 하고** 끝나면 배치를 만든다 — 그래서 커밋·push가 먼저다.
- 같은 경로에 이 레포·같은 산출물의 배치가 이미 있으면 새로 만들지 않고 성공으로 끝난다(다시 실행해도 안전). 같은 경로를 다른 배치가 쓰고 있으면 종료 코드 4 — 사용자에게 보고한다.
- 만든 배치는 **아직 라이브가 아니다.** 이어서 2b의 `bstage deploy`로 적용한다.
- 확인 규칙은 3절과 같다(기본은 `--yes` 없이 사용자가 확인창에 답하게 한다).
- 종료 코드 3이고 메시지가 토큰 등급을 말하면 deploy 등급 토큰이 아니거나 포털이 이 기능을 아직 지원하지 않는 버전이다 — 이때만 포털 화면(스테이지 > 페이지 > 새 페이지)을 안내한다.
- **레포 연결이 안 돼 있으면**(`bstage link`가 후보를 못 찾음) 포털 화면에서 스테이지 > 레포 > 새 레포 연결을 사용자에게 부탁한다(조직에서 처음이면 GitHub 앱 설치가 1회 선행).
- 위젯(슬롯) 자리에 거는 배치는 CLI로 만들지 않는다 — 포털 화면에서 슬롯 자리를 고른다. **liquid는 PAGE만** 가능하다.

### 2b. 배치가 있을 때

```bash
bstage deploy
```

순서는 이렇게 흐른다: git 사전점검 → 포털 빌드 트리거 → 빌드 완료 대기(로그를 따라 출력) → 배치에 적용.

- 특정 배치만 대상으로 하거나, 빌드만 걸고 끝내거나(대기 생략), 구조화 출력을 쓰려면 `bstage deploy --help`에서 해당 옵션을 확인한다.

## 3. 실행 규칙 (확인 없이 적용하지 않는다)

`bstage deploy`는 기본적으로 **무엇이 어디로 가는지 표로 보여주고 확인을 묻는다.** 이 확인 화면을 없애지 않는 것이 기본값이다.

- 기본: 배포 전에 네가 한 줄로 요약하고(어느 레포의 어느 커밋이 어느 스테이지의 몇 개 배치로 가는지), `--yes` **없이** 실행해 **CLI의 확인창을 사용자가 직접 보고 답하게** 한다.
- 사용자가 이미 명시적으로 확인했거나 비대화형 환경(CI)이면 `--yes`를 쓴다. 구조화 출력(`--json`)은 확인 프롬프트와 함께 쓸 수 없으므로 `--yes`와 함께 쓴다.
- 사전점검에 걸리면(커밋되지 않은 변경 · 기본 브랜치가 아님 · push되지 않은 커밋) **그 사실을 고친다.** `--skip-git-check`로 덮지 않는다 — 그 옵션은 "로컬과 원격이 다르다는 걸 알고도 원격 기준으로 빌드하겠다"는 선언이라, 사용자가 방금 고친 내용이 빠진 채 배포되는 대표적 원인이다.

## 4. 실패했을 때 — 종료 코드로 갈래를 잡는다

| 코드 | 뜻 | 대응 |
| --- | --- | --- |
| 0 | 성공 | - |
| 1 | 실패(빌드 실패 포함) | `bstage logs <빌드 id>` 또는 `bstage logs -f`로 원인 확인 후 코드 수정 → 커밋·push → 재배포 |
| 2 | 사전조건 미충족 | 메시지가 무엇이 빠졌는지 말한다(커밋·push·브랜치·배치 0건 → `bstage placement create`·산출물 이름·확인 불가 환경). 그 조건을 채운다 |
| 3 | 인증 | `bstage login` 다시. CI면 토큰 환경변수 설정 확인 |
| 4 | 충돌 | 대기하는 동안 다른 사람이 먼저 적용했다. **재시도부터 하지 말고** `bstage list`로 현재 라이브를 확인하고 사용자에게 보고한다 |
| 5 | 요청 제한 | 잠시 기다렸다 재시도 |

빌드 로그는 `bstage logs`로 본다(빌드 id 생략 시 최근 빌드, `-f`로 끝날 때까지 따라감).

배포는 성공했는데 API가 401로 실패하거나 페이지가 기대와 다르면(안 뜸·옛 화면) **추측으로 고치기 전에** `bstage doctor --json`을 실행한다. `portal.placements[].findings`의 `id`(예: `appkey.expired`·`env.not_rebuilt`·`build.update_pending`)로 원인을 가르고 `fix`가 말하는 조치를 따른다. `portal.status`가 `skipped`면 `hint`(로그인·링크)부터, `unsupported`면 포털이 아직 진단을 지원하지 않는 것이니 위 표와 로그로 되짚는다. `portal.status`가 `error`면 진단 자체가 실패한 것이다 — `reason`·`placements[].error`를 읽고, 권한 부족(401·403)이면 스테이지 관리 권한이 있는 계정인지·CLI 토큰 등급이 맞는지부터 확인한다. doctor는 진단에 error 항목이 있거나 `portal.status`가 `error`면 종료 코드 1로 끝난다(`skipped`·`unsupported`·warn·info는 0).

## 5. 되돌리기 · 게시 끄기

- `bstage rollback` — 직전 성공 빌드를 다시 라이브로 적용한다. 특정 빌드로 되돌리려면 빌드 id를 인자로 준다(`bstage list`에서 확인).
- `bstage publish off` — 게시만 끈다. 라이브 버전은 그대로 유지되므로, 화면을 급히 내려야 할 때 먼저 쓸 카드다. 되돌리려면 `bstage publish on`.
- 둘 다 기본으로 확인을 묻는다. 장애 상황이라 사용자가 이미 결정했다면 `--yes`를 쓰되, **무엇이 어떻게 바뀌는지 먼저 한 줄로 알린다.**
- 어느 쪽을 쓸지 헷갈리면: 잘못된 내용이 떠 있으면 `publish off`(즉시 내림) → 원인 파악 → `rollback`(직전 정상으로 복구).

## 6. CI에서 쓸 때

- 로그인은 대화형 대신 토큰 붙여넣기 경로를 쓴다. 연결 정보(조직·스테이지·레포 등)는 `.bstage/project.json` 대신 환경변수로 준다. **변수 이름은 `bstage login --help`·`bstage link --help`에 있는 것을 그대로 쓴다** — 여기 옮겨 적지 않는다(드리프트 방지).
- 비대화형이므로 `--yes`가 필요하고, 결과를 파싱할 거라면 `--json`과 함께 쓴다.
- 토큰은 CI 시크릿으로만 주입한다. 로그에 찍거나 저장소에 커밋하지 않는다.

# 하지 말 것

- 토큰을 출력·로그·커밋에 남기기 (`whoami`로 로그인 여부만 확인한다)
- `--skip-git-check`를 습관적으로 쓰기 — 사전점검이 잡는 건 "지금 고친 게 안 올라간다"는 사실이다
- 확인 프롬프트를 기본으로 `--yes`로 건너뛰기
- 종료 코드 4(충돌)를 그대로 재시도하기 — 남의 배포를 덮어쓸 수 있다
- 내가 맡은 배치 밖의 배치를 함께 적용·게시 전환하기 (범위를 좁히는 옵션은 `--help` 참조)
- 로컬 `dist/`를 어딘가에 업로드해 배포하려 시도하기 — 배포 경로가 아니다
- 배치가 0건인데 `bstage placement create` 없이 `deploy`를 반복하기
- 배치 삭제를 CLI로 시도하기 — 삭제는 포털 화면 전용이다
