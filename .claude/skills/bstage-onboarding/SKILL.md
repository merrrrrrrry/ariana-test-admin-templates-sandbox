# 역할

빈손에서 시작해 **첫 화면이 플랫폼에 뜨는 데까지** 사용자를 데려간다. 이 스킬은 순서와 성공 판정 기준만 담는다. 명령의 정확한 옵션은 항상 `bstage <명령> --help`를, SDK 사용법은 설치된 docs를 본다.

핵심 원칙:

1. **사용자는 개발자가 아닐 수 있다.** 파일·설정·설치 상태 확인은 **네(에이전트) 책임**이다. 직접 읽어 확인하고, 사용자에겐 제품·선호 **결정**만 구체적 선택지로 묻는다.
2. **확인이 안 되면 멈춘다.** 추측해서 다음 단계로 넘어가지 않는다.
3. **단계마다 성공 판정 기준을 먼저 말하고 확인한다.** "됐나요?"가 아니라 "이 출력이 나오면 성공"으로 말한다.
4. **되돌리기 어려운 일은 실행 전에 보여주고 확인받는다** — 원격 push, 배포, 게시 전환.

# 권위 있는 출처

- `bstage --help`, `bstage <명령> --help` — 명령·옵션의 유일한 출처(기억으로 옵션을 만들지 않는다)
- 설치 후 `node_modules/@bstage-sdk/core/docs/` — GETTING_STARTED·INIT·BUILD_SYSTEM 등. 목록은 `npx bstage docs`. SDK 의존이 없는 레포(예: `.liquid` 파일만 둔 레포)에는 이 경로가 없어 **종료 코드 2**로 끝난다 — 그때는 `bstage-liquid` 스킬이 규약·데이터·에셋을 들고 있다
- 프로젝트 규칙: 레포 루트의 `AGENTS.md`
- 이후 작업은 스킬로 넘긴다 — `bstage-template`(React 템플릿) · `bstage-liquid`(liquid 템플릿) · `bstage-deploy`(배포·롤백·게시)

# 절차

## 1. 결정 세 개를 한 번에 묻는다

작업을 시작하기 전에 아래 셋을 **한 번에** 묻는다(하나씩 물으면 사용자가 지친다).

- **(a) 어디에 붙이나** — 유저 플랫폼(방문자가 보는 화면)인지, 어드민(운영자가 보는 화면)인지.
- **(b) 어떻게 만드나** — 둘 중 하나를 고르게 하고 한 줄 장단점을 함께 준다.
  - **React 컴포넌트(sdk)**: 상호작용·상태·API 호출이 필요한 화면에 맞는다. 대신 빌드·번들 개념이 따라온다.
  - **liquid 템플릿**: 데이터를 받아 그려 주기만 하면 되는 화면에 맞는다. 배우기 쉽고 빠르지만 브라우저 쪽 로직은 제한된다.
- **(c) 어디에 배포하나** — 배포 환경(phase)과 스테이지 ID. 모르면 "포털에 로그인했을 때 보이는 스테이지 이름"이라고 알려주고, 1단계에서는 비워 둔 채 진행해도 된다(6단계에서 `bstage link`가 목록으로 물어본다).

한 레포에 두 방식을 함께 둘 수도 있다(혼합 레포) — 포털이 React 템플릿을 빌드한 뒤 liquid 템플릿을 함께 패키징한다. 다만 같은 화면을 두 방식으로 만들지 않고, sdk 페이지 폴더 이름에 `user`·`admin`을 쓰지 않는다(`src/pages/user`는 liquid 산출물 자리와 겹쳐 `bstage build`가 종료 코드 2로 막는다). 혼합 레포의 로컬 미리보기는 `bstage dev`(React)와 `bstage dev --kind liquid`로 따로 띄운다.

## 2. 프로젝트 생성

```bash
npx @bstage-sdk/cli@latest init
```

- CLI가 이미 설치된 환경이면 `bstage init`도 같다. 처음이라면 위처럼 `npx`로 최신 CLI를 바로 쓴다.
- 1단계 (b)의 결정은 `--kind sdk` 또는 `--kind liquid`로 넘긴다(기본은 sdk). 대상(유저/어드민)은 `--target`이다. 나머지 옵션은 `bstage init --help`로 확인한다.
- 대화형으로 스페이스·대상(유저/어드민)·첫 템플릿 이름·phase를 묻는다. 비대화형으로 돌려야 하면 옵션 이름을 추측하지 말고 `bstage init --help`로 확인한다.
- **성공 판정**: 새 폴더가 생기고 그 안에 `package.json`·`AGENTS.md`·`.claude/skills/`가 있다. 이후 작업은 **생성된 폴더 안에서** 한다(에이전트가 작업 디렉터리를 옮긴다).
- init이 에이전트용 스킬·`AGENTS.md`를 이미 설치해 둔다 — `bstage ai install`을 다시 돌릴 필요는 없다. `.claude/skills/`가 실제로 있는지만 확인한다.
- 의존성 설치가 끝났는지 확인한다(`node_modules`가 있는지). 설치가 실패했다면 원인을 읽고 사용자에게 보고한다 — 넘어가지 않는다.

## 3. 로컬에서 띄우고 한 군데 고쳐 본다

```bash
bstage dev
```

- `npm run dev`도 같은 일을 한다(프로젝트 스크립트).
- **성공 판정**: 터미널에 로컬 주소가 뜨고, 브라우저에서 목록·미리보기가 보인다.
- 사용자가 화면을 확인한 뒤, **눈에 보이는 문구 하나를 바꿔** 새로고침으로 반영되는 것까지 같이 본다. 이 한 번으로 "고치면 바로 보인다"는 감이 생긴다.
- 안 뜨면 추측하지 말고 터미널 오류를 읽는다. 포트 충돌이면 포트를 바꾸는 옵션이 있다(`bstage dev --help`).

## 4. 커밋하고 원격에 올린다

포털은 **원격 저장소에 push된 커밋**을 빌드한다. 로컬 파일은 올라가지 않으므로 이 단계를 건너뛸 수 없다.

- 아직 원격이 없으면 **사용자에게 결정을 묻는다**: 어느 조직(또는 개인 계정)에 만들지, 저장소 이름은 무엇으로 할지, 공개/비공개.
- 빈 저장소를 만든 뒤 원격을 추가하고 기본 브랜치에 push한다.
- **원격에 올리는 명령은 실행 전에 사용자에게 그대로 보여주고 확인을 받는다.** 어떤 저장소로 가는지 한 줄로 요약한다.
- **성공 판정**: 원격 저장소 기본 브랜치에서 방금 만든 파일이 보인다.

## 5. 포털에서 해야 하는 일 (레포 연결 — 화면에서만 가능)

레포 연결은 **포털 화면에서만** 할 수 있다. 사용자에게 순서를 알려주고, 끝났는지는 CLI로 확인한다. 포털 주소는 사용자가 쓰는 주소를 그대로 따른다 — 추측해서 적지 않는다.

1. **레포 연결** — 스테이지 > 레포 > 새 레포 연결. 조직에서 처음이라면 GitHub 앱 설치가 한 번 선행된다(조직당 1회).

**포털은 연결만으로 빌드하지 않는다.** 첫 빌드와 페이지(배치) 만들기는 7단계에서 CLI가 한다(`bstage placement create`). 이 화면 단계는 **새 레포에서 처음 한 번만** 필요하다.

## 6. CLI를 포털에 연결한다

```bash
bstage login
bstage link
bstage list
```

- `bstage login` — 터미널에 코드와 주소가 뜨고 브라우저가 열린다. 브라우저를 열 수 없는 환경이면 코드·주소만 출력하는 옵션이 있다(`--help`). 토큰은 사용자 홈의 설정 디렉터리에 소유자만 읽을 수 있는 권한으로 저장되고 화면에 찍히지 않는다.
- **1단계 (c)에서 정한 phase가 sandbox가 아니면** `bstage login`·`bstage link` 둘 다에 `--phase <phase>`를 준다. 생략하면 프로젝트 `.env`의 값을, 그것도 없으면 sandbox를 쓴다 — liquid 레포에는 스캐폴드된 `.env`가 없으므로 이 플래그가 특히 중요하다. 기본 목록 밖의 포털이면 `--portal`로 주소를 직접 지정한다(`bstage login --help`).
- `bstage link` — 현재 디렉터리를 조직·스테이지·레포에 연결하고 `.bstage/project.json`에 적는다(이 파일은 gitignore된다).
- **성공 판정**: `bstage list`가 이 레포의 조직·스테이지를 보여 준다(연결된 레포를 못 찾으면 5단계로 돌아간다). 새 레포라면 배치는 아직 0건이다 — 7단계에서 만든다.

## 7. 페이지(배치) 만들기와 첫 배포

```bash
bstage placement create --template <산출물 이름> --path /<경로>
bstage deploy
```

- `bstage placement create` — 이 레포의 산출물 하나를 페이지 배치로 만든다. 성공한 빌드가 없으면 push된 커밋으로 **빌드부터** 하고 끝나면 배치를 만든다. `--template`은 sdk는 `src/pages/{이름}`, liquid는 `public/{user|admin}/{이름}`의 `{이름}`이고, 경로(라이브 URL)는 사용자에게 확인한다. liquid는 **PAGE만** 가능하다. 다시 실행해도 같은 배치를 중복으로 만들지 않는다.
- `bstage deploy` — push된 커밋을 포털이 빌드하고, 빌드가 끝나면 이 레포의 배치에 적용한다. **로컬 빌드 산출물을 올리는 것이 아니다.**
- 두 명령 모두 기본으로 무엇을 어디에 적용할지 보여주고 확인을 묻는다 — 사용자가 그 화면을 직접 보게 한다.
- **성공 판정**: `bstage list`에 배치가 1건 이상 보이고 상태가 라이브이며, 스테이지 화면에서 바뀐 내용이 보인다.
- 자세한 규칙(실패 대응·롤백·게시 끄기·CI)은 `bstage-deploy` 스킬에 있다.

## 8. 이후 반복 루프

고친다 → 로컬에서 확인한다(`bstage dev`) → 커밋·push한다 → `bstage deploy`. 새 페이지를 추가했으면 push한 뒤 `bstage placement create`로 배치를 하나 더 만들고 `bstage deploy`한다. 포털 화면으로 다시 갈 일은 **위젯(슬롯) 배치·배치 삭제·새 레포 연결**뿐이다.

## 9. 막혔을 때

먼저 명령의 **종료 코드**로 갈래를 잡는다.

| 코드 | 뜻 | 먼저 할 일 |
| --- | --- | --- |
| 0 | 성공 | - |
| 1 | 실패 | 빌드 로그 확인(`bstage logs -f`) |
| 2 | 사전조건 미충족 | 커밋·push·브랜치·배치 유무를 점검(배치 0건이면 `bstage placement create` — 메시지가 무엇이 빠졌는지 말해 준다) |
| 3 | 인증 | `bstage login` 다시 |
| 4 | 충돌 | 다른 사람이 먼저 배포했다 — `bstage list`로 현재 상태를 보고 다시 판단 |
| 5 | 요청 제한 | 잠시 기다렸다 재시도 |

그 밖의 진단:

- `bstage doctor` — SDK 버전 드리프트·누락 파일 진단, 로그인·링크돼 있으면 배치별 포털 진단까지. 프로젝트 코드는 고치지 않지만 `--json` 없이 실행하면 SDK가 관리하는 스킬·`AGENTS.md` 관리 영역이 뒤처졌을 때 `bstage ai install`과 같은 동기화를 자동으로 한다
- `bstage ai doctor` — 스킬·`AGENTS.md`가 최신인지 확인(오래됐으면 `bstage ai update`)
- `bstage logs -f` — 최근 빌드 로그를 끝까지 따라가며 본다

# 하지 말 것

- 포털 화면에서만 되는 일(레포 연결·위젯 배치·배치 삭제)을 CLI 옵션으로 우회하려 시도하기
- 옵션 이름을 기억으로 지어내기 — `--help`로 확인한다
- 원격 push·배포를 사용자 확인 없이 실행하기
- 사용자에게 "코드가 맞나요"처럼 개발 지식이 있어야 답할 수 있는 것을 묻기 (확인은 네 몫)
- `bstage list`에 배치가 0건인데 `bstage placement create` 없이 배포를 시도하기
- 혼합 레포에서 sdk 페이지를 `src/pages/user`·`src/pages/admin` 아래에 만들기 — liquid 산출물 자리와 겹친다
