# 역할

이 프로젝트의 bstage SDK를 최신 버전으로 마이그레이션한다. 감지는 `bstage doctor`(결정론)가, 변환 절차는 SDK가 동봉한 `MIGRATION.md`가 정의한다. 너는 이 둘을 읽고 **이 프로젝트에 맞춰** 적용한다.

핵심 원칙:

1. **추측 금지 — 항상 실제 소스로 검증한다.** 모든 판단은 기억·가정이 아니라 **직접 읽어 확인한 사실**에 근거해야 한다. 변경 전에 (a) 설치된 패키지(`node_modules/@bstage-sdk/*`의 `MIGRATION.md`·`dist/*.d.ts` 타입 선언)와 (b) **이 프로젝트의 실제 소스 코드**를 직접 읽어 확인한다. SDK API·동작을 기억으로 단정하지 않는다.
2. **사용자가 작성/수정한 코드를 함부로 덮어쓰지 않는다.** 추가는 안전하게, 충돌·재구성은 확인한다.

확인이 안 되면 **추측해서 적용하지 말고 멈춘다.** 단, 사용자에게 "코드를 확인해 달라"고 떠넘기지 않는다 — 사용자는 개발자가 아닐 수 있어 직접 검증이 어렵다. **검증은 너(에이전트)의 책임**이다(파일·설치된 패키지를 읽어 스스로 확인). 사용자에겐 코드로 확인 가능한 *사실*이 아니라 **제품·선호 *결정*** 만, 구체적 선택지로 묻는다.

# 권위 있는 출처 (먼저 읽기)

- `MIGRATION.md` — 버전별 마이그레이션 항목·절차(단일 소스). 버전 범프+설치 후 `node_modules/@bstage-sdk/cli/dist/MIGRATION.md`(또는 core docs)에서 읽는다.
- `bstage doctor` — 현재 드리프트 진단(결정론). `npx @bstage-sdk/cli@latest doctor`.
- 문서 목록: `npx bstage docs` (SDK 의존이 없는 레포에서는 종료 코드 2로 끝난다 — liquid 레포라면 `bstage-liquid` 스킬을 본다)

# 절차

## 1. 진단 (doctor)

```bash
npx @bstage-sdk/cli@latest doctor --json
```

`bstage ai doctor`로 스킬·AGENTS.md가 최신인지도 함께 본다(stale이면 `bstage ai update`).

출력에서 네 가지를 얻는다.

- `versions` — 뒤처진 패키지와 latest 버전
- `files` — 누락된 보일러플레이트 파일
- `recommendedDeps` — 권장 의존성의 선언 상태(`declared: false`면 미선언). **버전 대조로는 안 잡히는 축**이므로 `migrations`가 비어 있어도 따로 확인한다
- `migrations` — 적용 가능한 마이그레이션 항목. 각 항목은 `label`(헤더 표기, 예: `cli 0.43.0` 또는 `core 0.32.0 · react 0.32.0`) · `requirements`(올려야 할 패키지·최소 버전 쌍) · `items`(항목 제목)를 가진다. 헤더의 패키지를 그 버전 이상으로 올린다

**종료 코드 1이어도 stdout의 JSON은 정상이다** — 로그인·링크된 레포에서는 포털 진단(`portal`)이 함께 돌고, 배치에 error 항목이 있거나 진단이 실패하면 1로 끝난다. `portal`은 배포된 배치의 상태라 마이그레이션과 무관하므로, 1이 나왔다고 진단을 실패로 보지 말고 JSON을 그대로 읽어 위 네 항목으로 진행한다(포털 문제는 따로 사용자에게 알리고 `bstage-deploy` 스킬로 넘긴다).

`isBstageProject`가 false면 bstage 프로젝트가 아니므로 중단한다. 레지스트리 조회에 실패해 `latestChecked`가 false면 버전 비교를 보류한다(보일러플레이트·항목은 계속 진행 가능).

## 1a. liquid 레포일 때

`bstage doctor`가 종류를 liquid로 판정하면 마이그레이션 범위가 다르다.

- 올릴 패키지는 `cli`뿐이다(core·react·design 의존이 없다). `versions`에 그것만 나온다.
- 보일러플레이트 파일 목록도 liquid 기준이다 — sdk의 `src/`·`vite.config.ts`가 없다고 만들지 않는다.
- `liquid` 검증 결과(문법·규약·경고)가 함께 나온다. error가 있으면 버전 작업보다 먼저 고친다 — 배포가 막히는 문제다.
- 스킬 세트는 `bstage-liquid`·`bstage-deploy`·`bstage-onboarding`·이 스킬이다. `bstage ai update`가 맞춰 준다.
- SDK 문서(`npx bstage docs`)는 SDK 의존이 없어 종료 코드 2로 끝난다 — 작성 규약·데이터·에셋은 `bstage-liquid` 스킬이 들고 있다.

## 2. 계획 제시 (승인 전 멈춤)

doctor 결과를 사용자에게 요약하고, **무엇을 할지** 계획을 제시한 뒤 승인을 받는다. 이때 사용자가 리뷰하는 것은 MIGRATION.md 원문이 아니라 **이 프로젝트에 맞춘 작업 계획**이다.

- 버전 범프 목록(현재 → 목표)
- 추가할 보일러플레이트 파일
- 적용할 마이그레이션 항목, 각 항목의 `자동`/`판단` 구분
- 판단이 필요한 지점(예: 커스텀 코드 교체)은 미리 짚어 둔다

## 3. 적용

### 3a. 버전 범프 + 설치 (자동)

`package.json`이 의존하는 `@bstage-sdk/*` 패키지를 모두 latest로 올린다 — 보통 `cli`/`core`/`react`/`design`이다. 버전 표기 스타일(캐럿 vs 정확한 버전)은 프로젝트 기존 컨벤션을 따른다. `react`/`vite` 등 사용자가 관리하는 의존성은 **임의로 올리거나 내리지 않는다**(예: 프로젝트가 이미 더 높은 vite를 쓰면 init 기본값으로 다운그레이드 금지). 그 후 설치한다(프로젝트의 패키지 매니저).

> **install이 bstage와 무관한 peer 충돌로 실패**하면(예: 다른 SDK가 옛 react를 요구) 프로젝트 고유 제약이다. 강제 변경하지 말고 `--legacy-peer-deps`(npm) 등 그 프로젝트의 기존 설치 방식으로 재시도하거나, 판단이 필요하면 사용자에게 보고한다.

> 이 단계 직후 `node_modules/@bstage-sdk/cli/dist/MIGRATION.md`가 생긴다. 이후 단계는 이 파일의 해당 버전 섹션을 정독하고 따른다.

doctor의 `recommendedDeps`에 `declared: false`가 있으면 **사용자에게 묻고** 함께 추가한다. 이건 버전 범프로 저절로 들어오지 않는다 — 예: `@bstage-sdk/design`(디자인 토큰)이 없으면 AGENTS.md·`bstage-template` 스킬은 토큰을 쓰라고 안내하는데 정작 import가 실패한다. 이미 최신 버전인 프로젝트에서는 `migrations`가 비어 이 축만 남으므로, 마이그레이션할 게 없다고 판단하고 넘어가지 않는다.

### 3b. init 기본 파일 차이 (판단 — 강요 금지)

doctor의 "init 기본 파일" 항목은 **누락이 아니라 init 기본 구성과의 차이**다. 추가하기 전에 **프로젝트가 같은 목적을 다르게 달성했는지** 먼저 확인하고, 필요할 때만 추가한다.

- `src/vite-env.d.ts` — `tsconfig`의 `types:["vite/client"]`로 이미 처리 중이면 불필요.
- `eslint.config.js` — eslint를 쓰지 않는 프로젝트(예: prettier/타 린터만)엔 추가하지 않는다.
- `tsconfig.app.json` / `tsconfig.node.json` — 단일 `tsconfig.json`이 잘 동작하면 굳이 쪼개지 않는다. 분리할 경우 사용자 설정(경로 별칭 등)을 보존한다.

판단이 서지 않으면 추가하지 말고 사용자에게 확인한다.

### 3c. 마이그레이션 항목 (항목별로 자동/판단 분리)

`MIGRATION.md`에서 적용 대상 버전 섹션을 읽고, 각 항목의 **적용** 절차를 따른다.

- `자동` 단계는 그대로 수행한다.
- `판단` 단계는 **실제 프로젝트 코드를 읽고** 적용한다. 예: 커스텀 i18n 헬퍼가 있으면 용도(자체 문구 vs 플랫폼 문구)를 분류해 `useMessages`/`useBstageTranslations`로 이전한다. 애매하면 일괄 치환하지 말고 사용자에게 묻는다.
- `선택` 항목은 이 프로젝트에 필요한지 사용자에게 확인한 뒤 진행한다.

### 3c-1. 템플릿 디렉토리 구조 (판단 — 사용자만 답할 수 있는 것)

doctor의 `layout.legacyPresent`가 `true`면 `src/templates/`가 남아 있는 옛 구조다. 페이지는 `src/pages/{경로}/`, 위젯은 `src/slots/{아무 이름}/`으로 옮겨야 하고, 안 옮기면 `bstage build`가 엔트리를 찾지 못해 멈춘다.

**여기서만은 사용자에게 물어야 한다.** 이 스킬의 원칙은 "사실은 에이전트가 검증하고, 사용자에겐 결정만 묻는다"이지만, 이 항목은 **사실 자체가 프로젝트 소스에 없다**:

- 폴더 이름은 지금까지 아무 의미가 없었다 — 빌드가 임시 라벨로만 쓰고 버렸다. 그래서 `src/templates/home/`이 실제로는 `/landing`에 배포돼 있을 수 있다.
- 슬롯 배치는 코드에 선언하지 않았다(설계상 관리도구 몫이었다). 그래서 페이지인지 위젯인지도 소스로는 갈리지 않는다.
- 어드민 전용 `type: 'fullPage' | 'sharedNav'`는 레이아웃 구분이라 이 판단에 쓸 수 없다.

실제 매핑은 관리도구(bstage portal)에만 있다. `layout.legacyTemplates`의 폴더를 하나씩 짚어 묻는다.

- 먼저 **소스를 읽고 추정안을 만들어 제시한다.** 전체 화면을 그리는지 작은 조각인지, 컴포넌트 이름이 무엇인지는 네가 읽어서 알 수 있다. 사용자가 백지에서 답하게 두지 않는다.
- 위젯이라고 답하면 **자리 목록을 선택지로 제시한다.** 카탈로그는 SDK가 들고 있으므로 사용자에게 찾아오라고 하지 않는다 — `node_modules/@bstage-sdk/core`의 `SLOT_CATALOG_V2`(또는 `SLOT_CATALOG_V2.md`)를 읽어 `description`과 함께 보여준다.
- 페이지라고 답하면 **관리도구에 등록된 경로**를 묻는다. 이것만은 사용자가 관리도구를 봐야 한다 — 대신 "관리도구에서 이 커스텀 페이지의 경로를 확인해 주세요"처럼 어디를 보면 되는지까지 알려준다.
- 확인이 안 되면 추측해서 옮기지 말고 멈춘다. 경로가 틀리면 배포 후 화면이 안 뜨는데, 원인을 찾기 어렵다.

옮긴 뒤에는 개발용 진입점의 `import.meta.glob`(유저 프로젝트는 `src/App.tsx`, 어드민은 `src/main.tsx`)과 `route-preview.json`·`config-preview.json` 값을 함께 고친다(MIGRATION.md의 해당 항목 참조). 마지막에 `npx bstage build`를 돌려 산출물이 의도한 경로로 나오는지 확인하고, 그 목록을 사용자에게 보여준다.

> 관리도구가 현재 매핑을 조회하는 API를 열면 이 물음은 자동 조회로 대체할 수 있다. 그때까지는 사용자에게 묻는 게 유일한 방법이다.

### 3d. AGENTS.md 관리 영역 동기화

`AGENTS.md`는 **SDK 관리 영역**(마커 `BSTAGE:MANAGED:START`~`END`로 감싼 SDK 저작 보일러플레이트)과 **자유 영역**(마커 바깥, 프로젝트 고유 규칙)으로 나뉜다. doctor의 `agentsMd.status`로 분기한다.

- `ok` — 할 일 없음.
- `stale` (마커는 있고 버전만 낮음) — **자동**. `bstage ai update`를 실행하면 관리 영역만 최신으로 치환되고 자유 영역은 보존된다. 끝.
- `legacy` (마커 없음 — 옛 프로젝트) — **판단**. SDK 내용과 사용자 내용이 한 덩어리라 1회 reconcile이 필요하다. **경계는 네(에이전트)가 먼저 분류해 제안하고, 사용자에겐 확인만 받는다** — 사용자에게 "어디까지가 프로젝트 추가분이냐"를 백지에서 묻지 않는다(사용자는 AGENTS.md 구조를 모를 수 있고, 분류는 네 책임이다).
  1. doctor `--json`의 `agentsMd.managedBlock`이 적용할 **최신 SDK 관리 영역(마커 포함)**이다. 이걸 레퍼런스로 삼아, 옛 AGENTS.md의 각 구간이 **SDK 보일러플레이트**(프로젝트 개요·SDK 문서 목록·프로젝트 구조·템플릿 작성 규칙·금지 사항·옛 `client.get('/api/...')` 예시나 엔드포인트 목록 등 — managedBlock이 대체하는 것)인지, **프로젝트 고유 내용**(이 레포만의 규칙·도메인 메모 등)인지 분류한다.
  2. 분류 결과로 "맨 위 = managedBlock, 그 아래 자유 영역 = 프로젝트 고유 내용만" 구조의 재작성안을 만든다. SDK 보일러플레이트는 managedBlock이 대신하므로 **자유 영역에 중복 보존하지 않는다** — 특히 옛 `/api/` 경로 목록이 남으면 재발 원인이 된다.
  3. 자유 영역으로 보존하려는 항목(=네가 "프로젝트 고유"로 분류한 것)을 사용자에게 제시하고 **경계를 확인받는다**: "이 부분들을 프로젝트 고유 내용으로 보고 보존하려는데 맞나요? SDK 영역으로 빼도 되는 게 섞여 있거나, 빠진 게 있나요?" (이건 "코드가 맞냐"는 검증이 아니라 "이게 너희가 추가한 거냐"는 소유 확인이라 사용자가 답할 수 있다.) 애매한 구간은 임의로 지우지 말고 자유 영역에 남겨 후보로 제시한다.
  4. 확인·조정 후 재작성하고, 최종 diff를 보여준다.

## 4. 검증

- 설치가 끝났는지 확인하고, 프로젝트의 타입체크·린트·빌드를 돌려 깨진 곳이 없는지 본다.
- `npx @bstage-sdk/cli@latest doctor`를 다시 돌려 버전이 최신으로 정리됐는지 확인한다(init 기본 파일 차이는 의도적으로 남길 수 있다).
- 남은 `판단` 항목(예: 도입을 보류한 선택 기능)이 있으면 사용자에게 보고한다.

# 하지 말 것

- **기억·가정으로 적용하기** — 설치된 패키지(`MIGRATION.md`·타입 선언)와 프로젝트 실제 코드로 확인하지 않고 변환하기
- **사용자에게 코드 검증을 떠넘기기** — "이 코드 맞나요?"처럼 사용자가 직접 확인해야 답할 수 있는 질문하기 (사용자는 개발자가 아닐 수 있다 — 검증은 네 몫)
- 사용자 코드를 통째로 덮어쓰기 (특히 `src/pages/**`·`src/slots/**`, 커스텀 `shared`/`api` 등)
- 템플릿이 페이지인지 위젯인지, 페이지면 어느 경로인지를 **추측해서** 옮기기 (관리도구에만 있는 정보다)
- 한 번에 모든 변경을 적용하고 검증을 건너뛰기
- `판단` 항목을 사용자 확인 없이 추측으로 변환하기
- `.bstage/i18n/**/*.json` 같은 재생성 가능한 캐시를 손으로 편집하기 (`bstage i18n pull`로 생성)
